# Security contracts and evidence

A JUnit execution record and a security validation record are different evidence. `TestEvidence` says only that a linked test invocation completed and whether JUnit reported it as passed or failed. It does not establish what was exercised. `ScenarioEvidence` records the HTTP response from a request executed by `AuthorizationChecks.verifyScenario`; the request is matched against a separate, consumer-authored policy row. The core evaluator uses no LLM or source-code trust heuristic.

`.cig/contracts.tsv` has six UTF-8 tab-separated fields: `id`, `severity`, `scope`, `description`, comma-separated `testIds`, and comma-separated `scenarioIds`. `.cig/scenarios.tsv` defines one policy per required scenario, with ten fields: `scenarioId`, `contractId`, `testId`, `type`, `actor`, `resourceOwner`, `resource`, exact `operation` (`METHOD /path`), optional `actorHeader`, and `expectedStatus`. An empty `actorHeader` verifies the authenticated servlet principal. V1 contract scenario support is `CROSS_OWNER`; cross-owner requires distinct actor and owner. Keep each manifest reviewed independently from its test implementation.

Register `EvidenceExtension`, annotate the real JUnit method with `@ContractTest("stable.test.id")`, and call `AuthorizationChecks.verifyScenario("scenario.id", mockMvc, request)` inside it. Configure the Surefire and (when used) Failsafe forks with `cig.evidence.file`, `cig.scenario.evidence.file`, `cig.scenarios.file`, and `cig.run.manifest.file`. Bind Maven goals in order: `prepare-evidence` at `initialize`; test goals; `seal-evidence` then `audit` at `verify`. Declare the CIG plugin after Failsafe so its verify goals run after Failsafe's `verify`. For Spring Security, use `SecurityMockMvcRequestPostProcessors.user(...)` and an empty actor-header column; the helper checks the authenticated principal name. With a header configured, it checks the HTTP header instead. The helper performs the request itself, checks method/path and actor/owner distinction, and records actual HTTP status tied to a process-unique JUnit invocation ID. It does not automatically detect IDOR or general authorization defects. Missing policy/observation or mismatched test/invocation cannot verify a contract.

`prepare-evidence` generates a random run UUID per Maven project/module and removes previous evidence files, even when `mvn clean` is omitted. The manifest records project coordinates, Maven-session identity, Maven process PID and OPEN state. Test JVMs must be the Maven process itself or one of its descendants before they can append; this prevents an older concurrent fork from adopting a newer run manifest. Forks read this file from disk and append Base64-safe UTF-8 TSV rows using OS file locks; they do not rely on shared memory. `seal-evidence` runs only after successful test phases, closes the run and records SHA-256 digests. `audit` requires the same Maven session, project origin, SEALED state, unchanged digests, complete strict-format records, unique invocation keys, and scenario/test rows from the same run and invocation. Separate modules use separate run IDs and output files; V1 does not aggregate evidence across modules.

Evidence format v2 has six tab-separated Base64URL-without-padding columns per line. JUnit rows are `runId`, `projectOrigin`, `testId`, `outcome`, `invocationId`, `detail`; scenario rows are `runId`, `projectOrigin`, `scenarioId`, `testId`, `invocationId`, `observedStatus`. Each record ends with LF. Empty, malformed, missing-field, invalid-UTF-8, wrong-run/origin, duplicate-key or unterminated final rows invalidate the evidence set. The report decodes these into readable JSON/HTML and includes run UUID and project origin.

| Result | Rule |
|---|---|
| VERIFIED | All linked test executions passed and each declared scenario has a matching policy-bound HTTP observation with the expected status, attached to a passing invocation. |
| FAILED | A linked JUnit invocation failed, or an observed scenario status/policy linkage mismatched. |
| UNVERIFIED | The contract declares no linked test IDs. |
| INCONCLUSIVE | Execution is incomplete, a linked test is missing/skipped, scenarios are absent, or policy/observation evidence is missing. |

An `assertTrue(true)` can at most produce execution evidence. Without the independently declared scenario and actual request observation, the contract is INCONCLUSIVE. `VERIFIED` means only that the declared scenarios returned their expected responses against the exercised fixture in the current sealed Maven invocation. It does not prove the application secure, prove the fixture represents production, or cryptographically establish evidence provenance. A consumer can author a wrong policy; reviewers must assess policy quality and fixture fidelity. Anonymous and insufficient-privilege scenario types are outside V1. Missing, old-session, unsealed, malformed, truncated, duplicated, conflicting, skipped, partial, wrong-origin, or post-seal-modified evidence cannot produce VERIFIED.
